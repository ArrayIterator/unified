## Guard idiom

Gate-only modules: every record type in these eight modules carries
no `company_id` / `tenant_id` field (map Scope column "none"), so
there is nothing to scope-check a record against. The guard is the
fail-closed tenant gate, exactly the `company` module's gate-only
model: `let _tenant = require_tenant(&req)?;` FIRST in every handler,
before any identity or capability call. `require_tenant` resolves the
middleware-attached tenant context (`TenantContext::from_http_request`,
401 without resolved context, 403 on a non-uuidv7 tenant id) and
never falls back to `public`. No `X-Company-Id` header is read
anywhere in this work.

**Deliberate decision, flagged for the coordinator:** no
`caller_company` call and no resolved-company requirement were added
to these handlers. That follows the cited gate-only model
(`company/handlers.rs`: `create_company` gates with `require_tenant`
only) and the pilot-3 gate-only precedent (hosting `create_plan`
gates with `require_tenant` only). The brief's "writes require a
resolved company" clause belongs to the scoped rule (a write naming
a company must match the caller scope); on records with no company
field there is nothing to verify a company against, so enforcing
`Some(company)` on every write would be a new behaviour — platform
admins / callers with tenant context but no company would lose write
access, which is task-315 (ControlPlaneGuard) territory, not a C3
gate decision. If the coordinator wants the stricter rule for these
modules, it is a one-line follow-up per handler
(`caller_company(&_tenant, &req)?` + require `Some`), and the
`require_tenant` helper already exists in all eight modules.

Each module's helper file carries the shared `require_tenant`
definition copied from `products/helpers.rs` (pilot 2) /
`company/requests.rs` (pilot 3), with a module-specific doc note
stating the gate-only reason, plus a `tenant_guard_tests` module
(fail-closed without context, resolve from middleware context).

Handler shapes gated (the gate line goes before the first
identity/capability call in each shape):

- Closure shape (hr 62, marketing 53, assets 28): `let result =
  (|| { let caller = caller(&req)?; ... })()` → `let _tenant =
  require_tenant(&req)?;` inserted before `let caller` (including
  the `let _caller` variants in hr `get_org_chart`,
  `list_review_cycles`, `get_review_cycle`).
- Closure shape, actor (webinars 43, meetings 28): `let actor =
  actor_id(&req)?;` (incl. `let _actor`, bare `actor_id(&req)?;` in
  webinars `update_config`, and `async` closures in meetings
  `attach_recording` and panels) → gate line inserted before it.
- Direct shape (site_builder 17, seo 6, panels 8, webinars 3,
  meetings 3): handlers that check auth with an early-return
  `if let Err(error) = ...` / `match ...` instead of a closure got
  the 3-line if-let gate block first, returning the module's error
  expression (`api_json::error_response(&error, ctx.is_debug())`
  for site_builder/seo, `json::error_response(&error, debug)` for
  panels, `err(error)` for webinars/meetings). This covers
  webinars `list_webinars` / `get_webinar` / `get_config`,
  meetings `list_rooms` / `get_room` / `meetings_ws`, panels
  `list_kinds` / `list_connections` / `get_connection` /
  `get_record` / `get_sync_status`, and the six macro-generated
  panels list handlers (gate inside the macro definition).

`meetings join_by_token` is gated, not excluded: it already requires
a verified caller (`let _actor = actor_id(&req)?;`) — the join token
is an additional credential, not a replacement for authentication.
`panels list_kinds` is gated, not excluded: it already requires
`authorize_view`, so it is an authenticated catalogue, not a public
surface (unlike pilot 2's unauthenticated `list_methodologies`).

## Exclusions (documented public / token surfaces, NOT gated)

- marketing `unsubscribe` — dual-path handler: the recipient path
  is anonymous by design (a signed unsubscribe token verified by
  `state.verify_unsubscribe_token` IS the authorization; route doc:
  "Record unsubscribe (admin, or recipient with a signed token)").
  Gating it would break anonymous recipient unsubscribes. The admin
  path already requires `caller` + `PERM_MARKETING_MANAGE`.
  Same class as the newsletter unsubscribe / public-form exclusions
  in pilots 1–3.
- site_builder `render_page` — public page render by design:
  published pages render for anyone; drafts / non-visible pages
  return 404 unless the caller holds `PERM_SITE_BUILDER_MANAGE`
  (checked with `.is_ok()`, i.e. auth failure only hides the page,
  it never errors). Same class as pilot 3's `render_table`
  exclusion. Gating it would break the public render endpoint.

No other handler in the eight modules is a public surface: every
other routed handler already required a verified caller and (except
webinars/meetings, which use `actor_id` + membership checks) a
capability check.

## Residuals (honest, not partitioned by the guard alone)

- All eight modules: records carry no company field, so the guard
  is a tenant gate only — a company-scoped caller can still read and
  write another company's records in these modules. Real
  partitioning needs a `tenant_id` on the records (C11 follow-up),
  as the map already notes.
- A caller with a resolved tenant context but no company (e.g. a
  platform admin) can still read and write in these modules — the
  gate does not require a resolved company (see the flagged decision
  above; task 315).
- marketing `unsubscribe`'s admin path is unchanged (caller +
  `PERM_MARKETING_MANAGE`); its anonymous token path stays
  ungated by design — a leaked unsubscribe token still unsubscribes
  that one recipient, which is the feature working as intended.
- site_builder `render_page` stays public for published pages by
  design; unpublished content is hidden by returning 404, not by
  an auth error.
- meetings `join_by_token` still resolves any valid join token for
  any authenticated caller (the token, not the caller, authorizes
  the join); the gate only adds the tenant-context requirement.
